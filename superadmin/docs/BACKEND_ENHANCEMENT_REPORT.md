# Backend enhancement report

Reviewed 04 Nov 2026. Static source/contract audit only; no live API, database or migration was executed. Backend and Prisma files remain unchanged. Paths below are relative to repository root. The review follows the API Engineering skill's contract-first approach, using local controllers, DTOs, services and schema as evidence; a separate Postman workspace was not needed for this read-only audit.

## Verified existing capabilities

All endpoints use `/api/v1`. Platform JWT and role guards protect platform modules; auth login is public. `backend/src/main.ts` applies global transformed/whitelisted DTO validation. Do not infer absent validation merely because a controller omits a local ValidationPipe.

JWT validation already verifies issuer, audience, algorithm, token type, current account status, current role and tokenVersion. Logout increments tokenVersion, invalidating prior tokens. This is not a missing revocation mechanism. Customer status mutations and support mutations write AuditEvent transactionally. Offers and settings have dedicated history tables rather than entries in the general audit feed.

## Ranked enhancements

### P0 — Required before presenting the whole console as production complete

1. **Platform password recovery and abuse protection.** Auth has login/me/logout only. PlatformUser has no reset-token relation; PasswordResetToken belongs to business User. Add a platform-specific hashed, expiring, single-use token/OTP flow and generic reset-request responses, attempt limits and invalidation. The inspected platform login service performs bcrypt lookup without the business login throttle; reuse a scoped throttle rather than assuming LoginThrottle automatically protects this controller. Add platform login/logout/recovery security events. Refresh-token support is optional; current short-lived access tokens already expire and revoke correctly.

2. **Plan catalog and subscription administration.** No platform plans controller/service exists. Existing `backend/src/common/plan-limits.ts` already provides static starter/growth/scale capacity limits, usage counts and enforcement helpers; `backend/src/modules/subscriptions/subscriptions.controller.ts` exposes a business-admin current-subscription view. Reuse these semantics rather than claiming capacity enforcement is absent. Unknown plan IDs currently resolve to no limit; catalog validation should prevent that fail-open case. BusinessSubscription stores planId and billingCycle as strings, status and timestamps only (`backend/prisma/schema.prisma`, BusinessSubscription). Add a Plan model/catalog with price/currency, limits, modules, enabled state and version; authenticated platform CRUD; transactional assignment/change/renew/cancel operations with usage-limit checks and audited reasons. Model trial start/end, current period boundaries, renewal/grace dates, cancel-at-renewal and auto-renew only with explicit semantics. Existing business subscription code is tenant-facing and does not establish a platform administration contract.

3. **Safe internal support notes.** SupportTicketMessage has authorId/message/createdAt, no internal/visibility field. CreatePlatformTicketReplyDto accepts a message only; current replies are customer-visible. Add persistent message visibility, enforce it on all business and platform reads, resolve author type/name, and audit writes. SuperAdmin currently rejects internal-note saves in API mode, so notes cannot accidentally become public replies.

4. **Billing settlement and redemption.** `platform/billing/payments` is explicitly a paid-invoice view, not a payment ledger. BillingInvoice has amount/status/dates/paymentNote, no transactional payment records, invoice lines/tax breakdown or redemption relation. Add idempotent gateway events, settlement/refund ledger, retries/reconciliation and subscription transition logic before exposing payment collection or confirmation. MarketingOffer is definition-only: no redemption counter/usageCount is stored. Define checkout validation, scope, usage reservations and atomic redemption linked to settlement. Never derive redemption counts from offer creation/history.

### P1 — Workflow coverage and contract consistency

5. **Support customer access policy.** Customers controller is admin-only; SuperAdmin's support role historically includes customer read access. Decide policy explicitly. If permitted, add a minimized read-only customer projection authorized for support; keep status/licence mutations admin-only. Current UI explains the restriction and suppresses unauthorized directory requests. Do not broadly grant support access to billing or plan endpoints.

6. **Prospects and campaigns.** `platform/marketing` implements offers only. Tenant CRM Lead and Customer are business records, not platform acquisition records. Add distinct platform Prospect, FollowUp and Campaign models/controllers, contact/source/stage/owner/history, optional offer reference and nullable start/end schedule fields. Support search/stage/date filters before pagination. Use date-only semantics for follow-ups; define a timezone separately if campaign execution gains a time-of-day. Saving a registry entry must not imply that email or advertising was sent.

7. **Dashboard metrics.** Existing summary lacks MRR, trial/expiry/attention counts, unpaid amount and revenue time series. Add period/granularity and currency-specific totals with documented recognition rules, subscription/customer counts distinguished, and server-side pending actions. All-current paid aggregate in the existing service is not sufficient for a monthly revenue trend. Add a support-only summary projection if more restricted metrics are needed; current support summary is usable today.

8. **Customer completeness.** Existing list includes companyCount/userCount; detail includes company branchCount. Full usage (employees/branches/companies/users), owner contact and subscription dates are absent. Add the minimum agreed projection, avoid exposing salary/bank/tenant CRM details, and supply a bounded company/branch directory. Validate account/profile editing fields only if a separate profile-edit endpoint is introduced. Existing status updates are already implemented and audited.

9. **Offer lifecycle and editing.** Current rules are DRAFT -> ACTIVE/ARCHIVED, ACTIVE -> PAUSED/ARCHIVED, PAUSED -> ACTIVE/ARCHIVED, ARCHIVED terminal. Content edits are limited to DRAFT/PAUSED; update supports title/description/start/end/usageLimit, not code/discount. SuperAdmin now respects these constraints and retains actual start/status. Consider an atomic edit/status command with expectedVersion to avoid partial multi-request saves. Add explicit title/description, scope and fixed-discount creation to the UI contract if required; current UI primarily creates percentage subscription offers. Preserve immutability of redeemed financial terms. Offer start/end ordering and percentage cap are already validated server-side.

10. **Global audit coverage and details.** AuditEvent exists with changes/scope/target. General feed excludes MarketingOfferChange and PlatformSettingChange unless separately aggregated. Add an actorType/name projection, centralized platform events or a unified feed adapter, and a free-text search separate from exact action. Existing event-detail endpoint already returns richer details; SuperAdmin's new sheet initially displays loaded list fields only. Consider paginated JSON changes for large events. Current inclusive UTC date boundaries already reject impossible/reversed ranges.

11. **Settings completion.** Phone, portal, announcement and display flag already exist and are now exposed. Trial signup toggle is absent in DTO/storage defaults and must be implemented consistently with onboarding. Consider optimistic version checks: server writes serialize correctly today, but sequential clients can still overwrite each other's values without an expectedVersion. Keep payment/email provider secrets outside this UI.

12. **Invoice export and filtering.** Add server PDF/export contracts with authorization and immutable legal invoice content. Extend list filters with dueBefore/dueAfter or explicit derived overdue semantics; current status filter alone cannot express ISSUED + dueAt < now + paidAt null. SuperAdmin retains an explicitly page-scoped overdue filter and current-page CSV. Search currently matches invoice number/description, not customer display name. Add joins or a deliberate customer search parameter and a stable sort allowlist.

### P2 — Consistency, performance and quality

13. Standardize list envelopes and page bounds. Services mostly use page/limit with stable tie-breakers; cap deep offsets consistently or introduce cursors for large audit/invoice datasets. Add supported sort fields/directions to DTOs rather than accepting arbitrary Prisma orderBy. Keep filters server-side before pagination. Offers currently load up to 100 definitions in the UI; add paginated offer selection/list contracts before large catalogs.

14. Add/verify indexes against measured query plans. Existing indexes cover subscription status; support tenant/company/status/update time; billing tenant/issue and company/status/due; marketing status/start/end and scope; history date keys. Platform-wide status/update or issue-date queries may need additional composite indexes. Count and list should use a consistent transaction/snapshot where appropriate; support currently uses Promise.all outside a shared transaction. Paginate ticket conversations and offer history (currently capped at 100), and avoid unbounded relations.

15. Standardize machine-readable validation/conflict codes, correlation IDs and partial-operation responses. Existing exceptions and DTO constraints are useful; do not replace them with generic 200 responses. Closed tickets currently reject replies and resolved tickets reopen; expose those semantics consistently in tests. Repeated status writes and retry behavior should be idempotent where practical.

16. Add platform-focused contract/integration tests for role matrices, revoked/suspended sessions, reset abuse, cross-scope offer validation, impossible/reversed dates, pagination boundaries, concurrent edits, internal-note privacy and gateway idempotency. Existing tests under `backend/test/` cover broader business/API behavior but were inspected rather than executed in this UI-only task. No production credentials were used.
